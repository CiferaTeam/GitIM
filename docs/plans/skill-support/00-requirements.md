## Problem Statement

GitIM agents can currently exchange messages, cards, flows, and durable session state, but reusable working knowledge still lives inside each AI runtime's private skill, rule, or memory system. An agent that discovers a useful workflow cannot turn it into a workspace capability that other agents can inspect, reference, and improve through GitIM.

GitIM needs a shared Skill layer with these properties:

- An agent can sediment a reusable workflow through the CLI.
- Every active workspace member can discover and explicitly load shared Skills.
- Agents can propose improvements without being allowed to overwrite the published version.
- Published content, proposals, reviews, role changes, and archival remain auditable in Git.
- Chat users can type `/` to find a Skill and insert a stable Skill reference.
- Receiving agents recognize that reference and explicitly load the pinned Skill before responding.
- GitIM does not inject shared Skills into Codex, Claude, Gemini, Hermes, or any other runtime's native Skill directories or configuration.

This is a GitIM collaboration feature, not a replacement for runtime-native Skills.

## What Makes This Cool

A useful behavior discovered in one conversation can become a named, versioned team capability without leaving the IM:

```text
agent discovers workflow
  -> gitim skill create/propose
  -> Git records the candidate and discussion
  -> maintainer publishes an immutable revision
  -> user inserts skill:release-check@r-...
  -> receiving agent explicitly loads that exact revision
```

The resulting message remains reproducible: its reference resolves to the same Skill revision even after the Skill evolves.

## Constraints

1. **Separate capability layer.** GitIM Skills are accessed through GitIM CLI/API calls. The implementation must not write or link `.agents/skills`, `.claude/skills`, `.gemini/skills`, `.opencode/skills`, or equivalent runtime-native directories.
2. **Minimal provider prompt change.** Providers receive only the stable Skill-ref handling contract and CLI syntax. The Skill catalog and Skill bodies are never injected into the base prompt.
3. **Standard package content.** Each immutable revision contains an Agent Skills-compatible package rooted at `SKILL.md`, with optional `scripts/`, `references/`, and `assets/`.
4. **Explicit loading.** `skill list` returns bounded metadata. `skill load` returns `SKILL.md` plus a bounded resource index. Additional resources are fetched individually.
5. **No implicit execution.** Loading a Skill never executes a script, grants tools, or changes provider permissions. Script execution remains an explicit provider action under the provider's existing tool controls.
6. **Daemon-owned writes.** Shared Skill files are written only through daemon-backed GitIM operations. Direct filesystem edits are unsupported, consistent with other shared GitIM state.
7. **Git auditability.** Every content or control-plane mutation creates one attributable Git commit. Read operations do not create commits.
8. **Stable toolchain.** Shared validation and transition logic must compile on the repository's stable Rust toolchain.
9. **Bounded data.** Listing and loading must not place an unbounded number of Skills or resources into an agent context.
10. **Frontend consistency.** Skill UI follows `DESIGN.md`: restrained dark surfaces, existing typography, soft-blue interactive accents, comfortable spacing, and minimal motion.
11. **Shared protocol semantics.** Pure parsing, metadata validation, revision/proposal identifiers, and ref rules live in `gitim-core` and are exposed through `gitim-wasm`. Browser-daemon v1 provides snapshot catalog/ref presentation only; authoritative package loading remains a Runtime capability.
12. **Trust boundary.** GitIM permissions are protocol correctness controls for workspace collaborators. They are not a cryptographic security boundary against a principal that can bypass the daemon and push arbitrary Git commits.
13. **Online shared writes.** In a workspace backed by a remote, every Skill mutation requires the remote to be reachable. Offline Skill mutation and later semantic reconciliation are outside v1.

## Premises

### GitIM Skills are not runtime-native Skills

Runtime-native discovery paths, precedence rules, and permission behavior differ. GitIM therefore owns only a shared catalog and an explicit loading protocol. Native installation or linking is outside this feature.

### A chat reference is an instruction to load, not embedded Skill content

The stored reference format is:

```text
skill:<slug>@<revision-id>
```

Example:

```text
skill:release-check@r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
```

The `/` character is a frontend discovery gesture only. Selecting `/release-check` inserts the canonical pinned reference into the message.

An unpinned `skill:<slug>` reference is accepted for manually authored messages and resolves to the current published revision at load time. GitIM-generated references are always pinned.

### Reads, proposals, publication, and execution are different authorities

- Reading and loading are workspace-wide.
- Proposing a revision is open to every active member.
- Publishing is limited to the Skill's owners and maintainers.
- Changing owners, maintainers, or archival state is limited to owners.
- Loading content never authorizes script execution.

### Published revisions are immutable

Published and proposed package snapshots are content-checked immutable objects. A proposal points to an immutable candidate revision. Publication only changes the Skill's current-revision pointer and proposal state.

### Concurrent semantic edits must not be auto-merged

`SKILL.md` is executable instruction content. GitIM must never insert conflict markers, perform last-writer-wins replacement, or ask an LLM to merge it automatically during sync. To replace a stale proposal, the contributor creates a new proposal against the current revision and then withdraws the old proposal; v1 has no automatic proposal rebase.

## Selected Architecture

### Storage Layout

```text
skills/<slug>/
├── skill.meta.yaml
├── history.thread
├── revisions/
│   └── r-<ulid>/
│       ├── revision.meta.yaml
│       └── package/
│           ├── SKILL.md
│           ├── scripts/
│           ├── references/
│           └── assets/
├── publications/
│   └── r-<ulid>.meta.yaml
├── proposals/
│   └── p-<ulid>/
│       ├── proposal.meta.yaml
│       └── discussion.thread

skills/workspace.meta.yaml
skills/receipts/
└── q-<ulid>.meta.yaml

archive/skills/<slug>/...
```

`package/` is the portable Agent Skills-compatible subtree. GitIM control metadata remains outside the package so exporting a revision does not leak workspace ownership or review state.

`skills/workspace.meta.yaml` is the repository-visible trust anchor for Skill
administrator recovery:

```yaml
schema_version: 1
administrators:
  - alice
control_revision: 1
created_at: "2026-07-30T04:00:00Z"
updated_at: "2026-07-30T04:00:00Z"
```

The Runtime initializes this file with the human workspace handler before the
first Skill mutation. Existing workspaces receive the same one-time bootstrap on
Runtime recovery. The bootstrap is valid only while no Skill objects exist and
creates an attributed Git commit plus a root
`skills/receipts/<request-id>.meta.yaml` receipt. Subsequent owner
recovery checks the administrator against this tracked file, so every daemon can
validate the same authority. Local `.gitim/me.json` admin state is never sufficient
on its own to authorize a repository-visible transition.

Bootstrap is the `workspace_bootstrap` operation in the same private-index
remote transaction machine as every other Skill mutation (or the local-only
transaction in a repository without a remote). It is never a working-tree
commit and therefore does not require an outbound-fence exception.

Workspace administrator changes are local Runtime CLI operations:

```bash
gitim-runtime skill-admin list --workspace <slug>
gitim-runtime skill-admin add --workspace <slug> --handler <active-handler> \
  --control-revision <n> --request-id <q-ulid>
gitim-runtime skill-admin remove --workspace <slug> --handler <handler> \
  --control-revision <n> --request-id <q-ulid>
```

Only a tracked administrator may add or remove administrators. The list is
sorted, unique, and non-empty; removing the final administrator returns
`skill_last_admin`. Adding an administrator requires an active workspace member.
Each change increments the workspace `control_revision`, updates `updated_at`,
and creates a root request receipt. These operations are unavailable through the
agent CLI and public HTTP.

The first successful bootstrap fast-forward establishes the initial
administrator. A concurrent bootstrap refetches that result instead of adding a
second administrator implicitly; an existing administrator must add any
additional human handler explicitly. User archive and composite depart/burn
reject `skill_admin_role_present` before any side effect while the target remains
in the tracked administrator list.

Revision, proposal, and request identifiers use separate prefixed ULID namespaces:

- Revision: `r-<26 uppercase Crockford Base32 characters>`
- Proposal: `p-<26 uppercase Crockford Base32 characters>`
- Request: `q-<26 uppercase Crockford Base32 characters>`

References always store the full revision identifier. The UI may visually abbreviate it.

### Skill Metadata

`skill.meta.yaml` is the current control-plane snapshot:

```yaml
schema_version: 1
slug: release-check
display_name: Release Check
description: Verify a release candidate before publication.
created_by: alice
owners:
  - alice
maintainers:
  - alice
current_revision: r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
open_proposal_count: 0
open_proposal_ids: []
control_revision: 1
event_revision: 1
created_at: "2026-07-30T04:00:00Z"
updated_at: "2026-07-30T04:00:00Z"
```

Invariants:

- `created_by` never changes.
- `owners` is sorted, unique, and non-empty.
- Every owner is also a maintainer.
- `maintainers` is sorted and unique.
- A Skill has at most 32 owners and 64 maintainers.
- Every referenced handler is an active registered workspace member when added.
- `current_revision` points to a valid immutable revision under the same Skill.
- `open_proposal_count` equals the number of proposals in `open` state.
  Proposal creation increments it; publish, reject, and withdraw decrement it in
  the same transition. It never exceeds 100.
- `open_proposal_ids` is sorted, unique, has at most 100 entries, and contains
  exactly the open proposals. `open_proposal_count` equals its length.
- `control_revision` increases exactly once when published content, display metadata, roles, or archival state changes. Updating `event_revision` alone for proposal/discussion activity does not increment `control_revision`.
- `event_revision` increases exactly once for every Skill mutation, including proposal creation, proposal comments, and proposal state changes.
- Archived Skills retain their metadata and revisions under `archive/skills/`.
- A slug is reserved while present under either `skills/` or `archive/skills/`; archived slugs cannot be reused by `create`.

Removing or archiving a user is rejected while that handler appears in the
workspace Skill administrator list or in any active or archived Skill's `owners`
or `maintainers`. The checks run at the start of both the direct user-archive
handler and the composite depart/burn handler, before the latter writes leave
events or archives DMs. The composite path rechecks immediately before its final
user-archive commit. Roles must be explicitly transferred or removed first, so a
failed initial precondition cannot leave a partially departed user.

User archival is also a cross-object transition enforced by `guarded_push`.
Immediately before every phase-four push or retry, it evaluates the archive
commit against the authoritative remote tip and uses the root `skills/` tree OID
as its semantic read set. If a concurrent Skill/admin role change wins first,
the archive push becomes stale and rechecks; if archival wins first, the losing
role-add transaction observes an inactive target and fails. This closes the
multi-commit depart time-of-check/time-of-use window without holding a network
lock across earlier departure phases.

### Revision Metadata

`revision.meta.yaml` is immutable after creation:

```yaml
schema_version: 1
id: r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
skill: release-check
base_revision: r-01K1D61DQJ2V9J3ZB3QJ8CB6NW
content_sha256: "<64 lowercase hex characters>"
created_by: bob
created_at: "2026-07-30T04:10:00Z"
```

The initial revision has `base_revision: null`.

`content_sha256` is calculated from a canonical manifest containing each package-relative path, file length, and file bytes in lexicographic path order. A revision whose calculated hash differs from its metadata is invalid and cannot be loaded or published.

A revision becomes loadable through a `skill:` ref only after the same operation creates its immutable `publications/<revision-id>.meta.yaml` record. Proposed candidates remain inspectable through proposal commands and review APIs but cannot be loaded as a normal Skill or inserted by the frontend. This keeps publication authority meaningful.

### Publication Metadata

`publications/<revision-id>.meta.yaml` is immutable:

```yaml
schema_version: 1
skill: release-check
revision: r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
content_sha256: "<revision content hash>"
base_revision: r-01K1D61DQJ2V9J3ZB3QJ8CB6NW
proposal: p-01K1D8R2FK9YV3M4P8XJC4YSA0
published_by: alice
published_at: "2026-07-30T04:20:00Z"
```

The initial publication has `base_revision: null` and `proposal: null`. Path revision, metadata revision, revision-directory ID, and content hash must agree. The publisher must have publish authority in the immediately preceding accepted Skill state. Missing, mutable, duplicate, or mismatched publication records make the affected revision unavailable through normal `skill:` loads.

### Proposal Metadata

```yaml
schema_version: 1
id: p-01K1D8R2FK9YV3M4P8XJC4YSA0
skill: release-check
candidate_revision: r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
base_revision: r-01K1D61DQJ2V9J3ZB3QJ8CB6NW
summary: Add rollback verification.
status: open
created_by: bob
created_at: "2026-07-30T04:10:00Z"
updated_at: "2026-07-30T04:10:00Z"
state_revision: 1
resolved_by: null
resolved_at: null
```

Proposal statuses:

```text
open -> published
open -> rejected
open -> withdrawn
```

Only the proposal author may withdraw an open proposal. Owners and maintainers may publish or reject it. Terminal proposals never reopen.

Proposal comments append to `discussion.thread`. Every active member may comment. Comments do not modify proposal state.

A Skill may have at most 100 open proposals. The limit and catalog summary use
the validated `open_proposal_count` rather than scanning historical proposal
directories. Historical terminal proposals remain paginated and do not count
toward this limit. A proposal may be based on any previously published revision,
but only a proposal based on the current revision can publish.

Proposal creation increments `open_proposal_count` and `event_revision`.
Publish, reject, and withdraw each decrement `open_proposal_count`, increment
`event_revision`, update `open_proposal_ids`, and update the proposal state in
the same commit. The pure transition validator checks the counter/list delta and
cross-checks only the at-most-100 indexed proposal entries; terminal history is
never scanned to enforce or serve the count.

Publishing an open proposal is one atomic transition:

1. `proposal.state_revision` must equal the caller's expected proposal revision.
2. `skill.control_revision` must equal the caller's expected control revision.
3. `proposal.base_revision` and the candidate revision's `base_revision` must both equal `skill.current_revision`.
4. The candidate package must still pass validation and hash verification.
5. An immutable publication record is created for `proposal.candidate_revision`.
6. `skill.current_revision` changes to `proposal.candidate_revision`.
7. `skill.control_revision` and `skill.event_revision` each increment by one.
8. Proposal status becomes `published`; its `state_revision` increments by one and resolver fields are stamped.
9. `skill.open_proposal_count` decrements by one.
10. The publication record, Skill metadata, proposal metadata, history append, and Git commit publish together.

A stale response returns the current `current_revision`, `control_revision`, `event_revision`, proposal `status`, and proposal `state_revision` so the caller can refresh without guessing.

### Request Receipt Metadata

Every Skill or workspace Skill-administration mutation creates the
workspace-global `skills/receipts/<request-id>.meta.yaml`:

```yaml
schema_version: 1
id: q-01K1D8T6JBF39AX68E0HHNV17W
skill: release-check
actor: alice
operation: proposal_publish
request:
  proposal: p-01K1D8R2FK9YV3M4P8XJC4YSA0
  expected_proposal_revision: 1
  expected_control_revision: 3
  payload_sha256: "<hash of operation-specific content>"
result:
  current_revision: r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
  control_revision: 4
  event_revision: 12
  proposal_state_revision: 2
created_at: "2026-07-30T04:20:00Z"
```

Receipt ID and filename must agree. A workspace-administration receipt uses
`scope: workspace` instead of `skill`; a Skill receipt uses `scope: skill` and
the `skill` field above. Receipts are immutable and belong to exactly one
mutation commit. The root path makes request IDs unique across the entire
workspace, including archived Skills. `request` stores the complete typed
semantic inputs; large bodies and packages are represented by their validated
SHA-256 digest. A retry returns the prior result only when actor, operation,
target, expected revisions, and payload digest all match. Reusing a request ID
for any other workspace operation returns `request_id_conflict`.

### History

`history.thread` is the product-facing lifecycle timeline. It records:

- Skill creation and initial publication
- Proposal creation
- Proposal publication, rejection, and withdrawal
- Owner and maintainer changes
- Skill metadata changes
- Archive and unarchive

History entries are appended by the daemon in the actor's name. Machine state is derived from YAML metadata, not from parsing free-form history text.

The Git commit remains the authoritative content audit trail. A lifecycle mutation commits its affected metadata, immutable objects, and history append atomically.

Every mutation also creates one immutable request receipt containing request ID, operation kind, actor, typed request fingerprint, result revisions, and timestamp. The request ID appears in the receipt, commit trailer, and the mutation's thread entry when that operation appends one. A retry with the same request ID returns the recorded result only after its fingerprint matches. The introducing commit ID is recovered with a path-limited Git log lookup for that receipt, avoiding a circular commit-ID field inside the commit itself.

Read operations, including `list`, `show`, `load`, and `resource`, do not append history or create Git commits.

## Permission Model

| Operation | Active member | Proposal author | Maintainer | Owner |
|---|---:|---:|---:|---:|
| List/show/load current or previously published pinned revision | Yes | Yes | Yes | Yes |
| Read proposal and discussion | Yes | Yes | Yes | Yes |
| Create a new Skill | Yes | Yes | Yes | Yes |
| Create a proposal | Yes | Yes | Yes | Yes |
| Comment on a proposal | Yes | Yes | Yes | Yes |
| Withdraw own open proposal | No | Yes | If author | If author |
| Reject an open proposal | No | No | Yes | Yes |
| Publish an open proposal | No | No | Yes | Yes |
| Edit display name or description | No | No | Yes | Yes |
| Add/remove maintainers | No | No | No | Yes |
| Add/remove owners | No | No | No | Yes |
| Archive/unarchive Skill | No | No | No | Yes |

Create atomically stores the initial revision, creates its publication record, and makes the creator both owner and maintainer. Because loading remains explicit, creation does not alter any agent's base prompt or runtime-native configuration.

Role and archive mutations require the caller's observed `control_revision`. Proposal state mutations require the observed `state_revision`.

Role transitions obey these rules:

- `owner-add` adds the handler to both `owners` and `maintainers`.
- `owner-remove` removes the handler from `owners` but retains maintainer membership unless `--remove-maintainer` is also supplied.
- `maintainer-remove` rejects an owner; the owner role must be removed first in the same request or an earlier request.
- Removing the last owner returns `skill_last_owner`.
- Adding a role requires an active registered handler.
- User archival reports `skill_roles_present` while the handler appears in any active or archived Skill role list. The caller must transfer/remove those roles before retrying archival.
- Departed handlers are never added to new role lists. Historical `created_by`, revision authors, proposal authors, and history entries remain unchanged.

Archive moves the complete Skill subtree to `archive/skills/<slug>/`, then
increments `control_revision` and `event_revision` exactly once and stamps
`updated_at` before writing the receipt and history entry. Unarchive performs
the inverse move and the same revision/timestamp transition. The transition
validator requires the source path to disappear, the destination path to
contain the same immutable objects, and only the mutable metadata, root receipt,
and appended history line to differ.

The Runtime's human workspace handler is registered as the initial **Workspace
Skill Administrator** in `skills/workspace.meta.yaml`. The local Runtime
administrative CLI exposes:

```bash
gitim-runtime recover-skill-owner \
  --workspace <slug> --skill <skill-slug> \
  --new-owner <active-handler> --confirm

gitim-runtime repair-skill-state \
  --workspace <slug> [--skill <skill-slug>] \
  --conflict-tip <commit-oid> --accepted-tree <tree-oid> --confirm
```

This recovery path exists for a lost or unavailable sole owner. It is unavailable
through agent CLI and public HTTP. It requires the human handler to appear in the
tracked administrator list, runs through the same remote-ref transaction as every
other Skill write, adds the active handler as owner and maintainer, increments
control/event revisions, and records `owner_recovered` in history and Git under
the administrator's identity. The existing owner entry remains until the new
owner explicitly removes it, preserving auditability and preventing recovery from
silently rewriting ownership history.

`repair-skill-state` is available only when the local validation checkpoint
records the supplied conflict tip and accepted tree. Omitting `--skill` repairs
the tracked workspace Skill-administrator control state; providing it repairs
only that active or archived Skill subtree. The transaction preserves invalid
commits in Git history, adds an administrator-authorized repair receipt, and
restores the last accepted tree without trusting files from the conflicting
tip.

### Active and Archived Operation Matrix

| Operation | Active Skill | Archived Skill |
|---|---:|---:|
| List without `--archived` | Yes | Hidden |
| List with `--archived` | Yes | Yes |
| Show/load unpinned current ref | Yes | `skill_archived` |
| Show/load/resource pinned revision | Yes | Yes, with `archived: true` |
| Read history, proposals, and discussions | Yes | Yes |
| Create proposal or comment | Yes | `skill_archived` |
| Publish/reject/withdraw proposal | Yes | `skill_archived` |
| Edit display metadata | Yes | `skill_archived` |
| Edit roles | Yes | Owner only, for ownership cleanup |
| Archive | Yes | Already archived |
| Unarchive | Not applicable | Owner only |

Unarchive restores the same reserved slug. Because archived slugs cannot be reused, unarchive has no active-path collision case.

## CLI Contract

### Read Commands

```bash
gitim skill list [--archived] [--limit <n>] [--cursor <cursor>] [--json]
gitim skill show <slug> [--revision <revision-id>] [--json]
gitim skill load <skill-ref-or-shorthand> [--json]
gitim skill resource <skill-ref-or-shorthand> <relative-path> \
  [--json] [--output <path>] [--create-dirs] [--force]
gitim skill ref <slug> [--revision <revision-id>]
gitim skill validate --from <directory>
gitim skill revisions <slug> [--limit <n>] [--cursor <cursor>] [--json]
gitim skill history <slug> [--limit <n>] [--cursor <cursor>] [--json]
```

`skill-ref-or-shorthand` accepts either canonical `skill:<slug>@<revision-id>` or CLI shorthand `<slug>@<revision-id>`. Omitting the revision is allowed only for active Skills and resolves the current revision. `skill ref` and every JSON response emit only the canonical `skill:` form.

`list` returns only slug, display name, description, current revision, owners, maintainers, and proposal counts. It uses opaque cursor pagination with a default limit of 50 and a hard maximum of 100.

`load` returns:

- Canonical pinned ref
- Revision metadata
- Complete `SKILL.md`
- Resource index containing relative path, byte size, media type, and text/binary classification

It does not inline scripts, references, or assets.

`show --revision` and `revisions` expose published revisions only. Candidate
revisions are reachable only through the proposal inspection commands, so a
candidate cannot accidentally acquire a canonical `skill:` reference before
publication.

`resource` writes UTF-8 text to stdout. Binary resources require `--output`; the CLI does not print binary bytes to the terminal.

`proposal-resource` uses the same bounded output rules but reads only the candidate revision named by the proposal. It is an inspection operation: it never creates a canonical Skill ref, marks the candidate published, or executes content.

### Write Commands

```bash
gitim skill create <slug> --from <directory> \
  --display-name <name> --description <description>

gitim skill propose <slug> --from <directory> \
  --base <revision-id> --summary <summary>

gitim skill proposal list <slug> [--status open|published|rejected|withdrawn] \
  [--limit <n>] [--cursor <cursor>] [--json]
gitim skill proposal show <proposal-id> [--diff]
gitim skill proposal resource <proposal-id> <relative-path> \
  [--json] [--output <path>] [--create-dirs] [--force]
gitim skill proposal discussion <proposal-id> \
  [--limit <n>] [--cursor <cursor>] [--json]
gitim skill proposal comment <proposal-id> --body <text>
gitim skill proposal withdraw <proposal-id> --state-revision <n>
gitim skill proposal reject <proposal-id> --state-revision <n>
gitim skill proposal publish <proposal-id> \
  --state-revision <n> --control-revision <n>

gitim skill admin update <slug> \
  [--display-name <name>] [--description <description>] \
  --control-revision <n>

gitim skill role owner-add <slug> <handler> --control-revision <n>
gitim skill role owner-remove <slug> <handler> \
  [--remove-maintainer] --control-revision <n>
gitim skill role maintainer-add <slug> <handler> --control-revision <n>
gitim skill role maintainer-remove <slug> <handler> --control-revision <n>
gitim skill admin archive <slug> --control-revision <n>
gitim skill admin unarchive <slug> --control-revision <n>
```

All write commands accept `--request-id q-<ulid>` and support structured JSON responses. When omitted, the CLI generates an ID, prints it before dispatch, and stores the typed request fingerprint under `.gitim/request-journal/<request-id>.json`. A retry of the same command reuses its sole matching pending request; ambiguous matches require an explicit `--request-id`. The journal entry is removed only after a definitive success or domain failure.

Permanent validation, permission, and stale-revision failures map to the existing non-retryable CLI error class. Remote or transient sync failures remain retryable.

### Progressive CLI Discovery

The root `gitim skill --help` output stays task-oriented and shows only:

- Use a Skill: `list`, `load`, `ref`
- Create or improve: `create`, `propose`
- Inspect details: `show`, `resource`, `revisions`, `history`, `validate`
- Review changes: `proposal --help`
- Administer: `role --help`, `admin --help`

Nested help expands only the selected command group. Provider prompts never contain this command tree.

Successful command responses may return a bounded `next_actions` array containing commands relevant to that result. For example, `load` suggests `resource` only when the revision has additional resources, and `propose` suggests proposal review commands only after a proposal exists. `next_actions` is guidance, not executable content, and contains at most three entries.

Every Skill write request carries a client-generated request ID. The daemon includes it in the immutable receipt, Git commit trailer, and the operation's thread entry when one exists, so an uncertain client retry can discover the already-published result.

### Pagination and Text Bounds

- Skill and proposal lists: default 50, maximum 100.
- Revision history: default 50, maximum 100.
- Proposal discussion and Skill history: default 100 entries, maximum 200.
- Frontend slash results: maximum 20.
- Display name: 1–80 Unicode scalar values.
- Description: 1–1024 Unicode scalar values.
- Proposal summary: 1–500 Unicode scalar values.
- Proposal comment: 1–10,000 Unicode scalar values.
- Unified text diff response: maximum 256 KiB after rendering.

Every list response returns `next_cursor: null|string`. A changed catalog/proposal/history collection returns `stale_cursor`, after which the caller restarts from the first page.

## Package Validation

A package is valid when:

- `SKILL.md` exists and is valid UTF-8.
- Its frontmatter satisfies the Agent Skills name and description contract.
- Frontmatter `name` equals the GitIM Skill slug.
- All entries are regular files beneath `package/`.
- Symlinks, devices, sockets, path traversal, absolute paths, `.git`, and `.gitim` entries are rejected.
- File paths contain no control characters and are portable across supported platforms.
- Every path segment is 1–80 ASCII characters matching `[A-Za-z0-9][A-Za-z0-9._-]*`; the complete package-relative path is at most 240 bytes.
- `SKILL.md` is at most 64 KiB.
- Each file is at most 5 MiB.
- The package contains at most 256 files.
- Total uncompressed package size is at most 10 MiB.

Unknown frontmatter fields are preserved because GitIM stores the validated source
bytes exactly and never reserializes `SKILL.md`. GitIM parses frontmatter only for
validation and does not interpret runtime-specific fields such as `allowed-tools`.

Validation may warn about likely secrets, executable scripts, or binary assets, but deterministic structural violations are the only blockers in this version.

Every imported package file is stored with Git mode `100644`. Source executable bits and other filesystem mode bits are discarded, so content integrity and Git tree identity cannot diverge through mode-only changes. A provider may still explicitly run a text script through an interpreter under its existing tool permissions.

### Canonical Package Hash

The canonical manifest is a byte stream. For each regular file in lexicographic order by its validated UTF-8 package-relative path:

```text
u32_be(path_byte_length)
path_utf8_with_forward_slashes
u64_be(file_byte_length)
raw_file_bytes
```

Paths use `/` separators, are relative to `package/`, and are hashed without Unicode normalization or case folding. Validation rejects two paths that collide after ASCII case folding, Windows reserved names, trailing spaces or dots in a segment, NUL/control characters, `.`/`..` segments, and backslashes. Directories do not appear in the manifest. SHA-256 of the complete byte stream is stored as lowercase hexadecimal `content_sha256`.

### Local Package Import

`--from <directory>` is a local CLI-to-daemon operation:

1. The CLI resolves the path to an absolute directory and sends only that path plus metadata over the local Unix socket.
2. Before any network operation, the daemon canonicalizes the path, walks it without following symlinks, enforces file/count/size limits, and copies the validated bytes once into `.gitim/skill-transactions/<request-id>/source/`.
3. The immutable source snapshot is mode-normalized, hashed, and included in the request fingerprint. Transaction retries read only this snapshot; later edits to the caller's source directory cannot change the in-flight request.
4. The daemon never accepts a source path over Runtime HTTP in v1.
5. The request remains small; package bytes are not embedded as JSON or base64 in the newline-delimited daemon protocol.

The daemon and CLI run as the same local OS user, so reading the supplied local path does not expand the caller's filesystem authority. Package authoring through a remote browser/API is outside v1.

### Diff and Resource Output

- Text files produce a three-context-line unified diff.
- Binary, added, or removed resources produce path, size, media type, and content-hash records rather than byte diffs.
- A modified text file larger than 1 MiB on either side uses the same
  path/size/media-type/content-hash representation as binary content. This avoids
  unbounded line-diff CPU and memory while preserving reviewable change identity.
- A diff larger than 256 KiB returns the deterministic prefix plus `truncated: true`; it never truncates inside a UTF-8 scalar.
- Bounded text output uses a shared stable-Rust helper that walks backward with
  `str::is_char_boundary`; it does not depend on nightly-only boundary APIs.
- Media type uses one `gitim-core` extension table exported through wasm: `md/txt` → `text/plain` (`md` uses `text/markdown`), `json` → `application/json`, `yaml/yml` → `application/yaml`, `toml` → `application/toml`, `sh` → `text/x-shellscript`, `py` → `text/x-python`, `js/jsx` → `text/javascript`, `ts/tsx` → `text/typescript`, `rs` → `text/x-rust`, `png` → `image/png`, `jpg/jpeg` → `image/jpeg`, `gif` → `image/gif`, `webp` → `image/webp`, `svg` → `image/svg+xml`, and `pdf` → `application/pdf`. Unknown extensions use `application/octet-stream`.
- `skill resource --json` returns metadata and UTF-8 text content only. It rejects binary content unless `--output` is supplied.
- `--output` uses create-new semantics by default, creates parent directories only when explicitly requested with `--create-dirs`, and requires `--force` to replace an existing file.
- Output files use the caller's normal umask. GitIM does not preserve executable bits from a Skill package.

## Skill Reference Grammar

Canonical refs are case-sensitive and match:

```text
skill:<slug>[@<revision-id>]
```

Where:

- `<slug>` is 1–64 characters matching `[a-z0-9]+(?:-[a-z0-9]+)*`.
- `<revision-id>` matches `r-[0-9A-HJKMNP-TV-Z]{26}`.
- The preceding and following characters, when present, cannot be a Unicode letter/number, `_`, `/`, `\`, or `-`.

Examples:

```text
skill:release-check
skill:release-check@r-01K1D8QG2S8RX4T9M9BDKQ9Z7N
(skill:release-check@r-01K1D8QG2S8RX4T9M9BDKQ9Z7N)
```

The parser ignores refs inside inline code, fenced code blocks, URL destinations, and backslash-escaped text. Malformed, mixed-case, partial, or boundary-violating candidates remain plain text.

## Mutation and Conflict Semantics

### Remote Ref as the Transaction Coordinator

Remote-backed Skill writes do not add an in-process repository-wide lock. The
remote branch ref is the serialization point:

- Every candidate commit has the fetched remote tip as its only parent.
- A normal push accepts the commit only when it is still a fast-forward.
- Concurrent ordinary sync, epoch rotation, and another Skill transaction can
  make one writer lose the race, but cannot overwrite either writer's history.
- A losing Skill transaction retries only after comparing its complete semantic
  read set at the new remote tip.
- The existing `commit_lock` remains limited to mutations of the active working
  tree and index. Remote Skill transactions never use either.

This avoids coupling every existing push/fetch/rebase call site to a new async
lock. It also prevents a slow Skill network operation from blocking local message
commits. Git ref fast-forward rules provide the compare-and-swap boundary that the
protocol needs.

### Remote Workspace Transaction

Every Skill write in a remote-backed workspace follows this state machine:

1. Validate request shape, actor, request ID, and local source package before
   network work. Generate revision/proposal identifiers once, persist them in
   the journal, and reuse them for every retry.
2. Copy the validated package bytes once into
   `.gitim/skill-transactions/<request-id>/source/`; later retries use only this
   immutable snapshot.
3. Fetch origin and resolve the authoritative active epoch branch, following an
   epoch redirect before selecting a base. Repeat branch resolution after every
   non-fast-forward rejection; a retry never assumes that the epoch branch name
   stayed constant.
4. Record `remote_branch`, exact `remote_tip` object ID, and the object IDs of
   the mutation's semantic read set: active/archive Skill paths, tracked Skill
   administrator metadata when relevant, and referenced user metadata.
5. Return the recorded result immediately if the matching request receipt
   already exists at `remote_tip`.
6. Re-read Skill, proposal, role, archival, and administrator state using
   explicit `<remote_tip>:<path>` Git object reads.
7. Apply permission and expected-revision checks against that immutable state.
8. Create a private temporary Git index file under the request directory and
   initialize it with `git read-tree <remote_tip>`.
9. Write exact mutation bytes as Git blobs, update only allowed paths in the
   private index, call `git write-tree`, and create a single-parent commit with
   `git commit-tree -p <remote_tip>`. The active index, working tree, and local
   branch ref remain untouched. A history append parses the `history.thread`
   blob at that exact remote tip and allocates the next line number there; it
   never derives a line number from the active worktree.
10. Validate the candidate tree and receipt against the same pure transition
    validator used for incoming commits.
11. Push `<transaction-commit>:refs/heads/<remote_branch>` with a normal
    fast-forward push. Any intervening writer causes a non-fast-forward reject.
12. On rejection, fetch the new tip and compare every semantic read-set object
    ID. When only unrelated paths changed, rebuild the same typed request on the
    new tip, up to three transport retries. When any read-set object changed,
    return a stale response with the newly observed state. GitIM never replays a
    semantic mutation after its preconditions changed.
13. On push success, delete the private index and source snapshot, record the
    accepted read view, and notify normal sync to integrate the remote commit.

Git object construction and network subprocesses run inside bounded
`spawn_blocking` work. The async handler awaits the result without blocking a
Tokio worker. Ordinary local message commits and background sync may proceed
concurrently; the remote fast-forward check orders competing publications.

Remote transactions journal `prepared`, `built`, `pushed`, and `completed`
phases together with private index path, source snapshot path, remote branch/tip,
generated revision/proposal identifiers, candidate commit, request fingerprint,
and receipt path. Startup recovery:

1. Enumerates recorded journals before accepting Skill writes.
2. Checks the authoritative remote branch for the matching receipt and commit.
3. Treats a found matching receipt as published, records the accepted read view,
   and completes cleanup.
4. Removes only the recorded private index and source snapshot when the
   candidate was not published. The unreachable candidate objects are left for
   normal Git garbage collection.
5. Quarantines fingerprint mismatches or ambiguous remote state and reports them
   through runtime health.

The remote push is the publication point. A successful response contains:

```json
{
  "ok": true,
  "commit_id": "<remote commit>",
  "request_id": "q-<ulid>",
  "current_revision": "r-<ulid>",
  "control_revision": 4,
  "event_revision": 12,
  "local_state": "current | pending_sync"
}
```

If the post-push local refresh cannot complete, the mutation remains a success with `local_state: "pending_sync"` because the remote commit is already durable. A retry with the same request ID returns the original remote result by matching its immutable receipt and commit trailer instead of duplicating the mutation.

The daemon records the accepted remote commit as its Skill read view before
returning success. Until the active worktree's relevant Skill tree OID matches
the accepted checkpoint, Skill list/show/load/resource and proposal reads use
Git tree/blob reads at the accepted commit rather than stale or unvalidated
working-tree files. A catalog cache is keyed by that
view's commit ID; it is rebuilt at most once per view. `load` obtains its resource
index with one recursive `ls-tree` call and reads `SKILL.md` with one blob read,
instead of spawning one Git process per resource. Once normal sync integrates the
commit, a Skill read returns to the active worktree only when that Skill's tree
OID at `HEAD` exactly equals its accepted checkpoint tree OID. Merely containing
the accepted commit is insufficient because a later unvalidated Skill commit may
also be present; unrelated message commits may advance `HEAD` while preserving
the same Skill tree OID. This guarantees read-your-writes without exposing a
newer unvalidated subtree.

Open proposals and their immutable candidate revisions already stored before a `proposal-publish` transaction remain available when a stale publish loses. A failed `create` or `propose` transaction leaves the caller's source directory untouched and publishes no partial revision.

### Local-Only Workspace Transaction

A local-only workspace performs the same permission and revision checks against its active branch. It stages the complete mutation in a temporary directory, then holds `commit_lock` while:

1. Re-reading all preconditions.
2. Saving path-local backups and the prior index entries for affected Skill paths.
3. Installing the new files.
4. Committing only those paths.
5. Restoring files and index entries if the commit fails.

Rollback never uses repository-wide reset or checkout operations. A transaction
journal under
`.gitim/skill-transactions/<request-id>/transaction.yaml` records the base HEAD,
affected paths, backup manifest, expected receipt path, and `prepared`,
`installed`, or `committed` phase.

Startup recovery first searches HEAD/history for the request receipt and verifies its fingerprint. If the receipt's introducing commit exists, recovery finalizes the transaction even when the journal still says `installed`. It restores backups only when no introducing commit exists and HEAD/index checks match the recorded base; otherwise it quarantines the journal and reports a health error instead of overwriting committed files.

### Proposal and Control Concurrency

All remote Skill writes require the online transaction above, including proposal creation, comments, withdraw, reject, publish, metadata edits, role edits, archive, and unarchive. V1 therefore produces no legitimate unpushed Skill commits in a remote-backed clone.

Every operation may transport-retry on a new branch tip only while its complete semantic read set and typed request remain identical. Proposal creation therefore preserves the same immutable IDs, and comments preserve the same request ID. No operation retries after Skill, proposal, role-target, or expected-revision state changes.

Skill validation fences both directions:

- Every working-branch push, including direct daemon handler pushes and the sync
  loop's push-first path, routes through one `guarded_push` coordinator. Raw Git
  push remains available only to the private Skill transaction and epoch
  rotation with an explicit operation mode. The coordinator inspects the
  complete unpushed path set before any working-branch publication.
- Any local commit touching `skills/` or `archive/skills/` in a remote-backed
  workspace enters the local bypass-repair path. Legitimate v1 writes publish
  directly from the private-index transaction, so there is no valid exception
  to this rule.
- The same coordinator recognizes active-to-archived user metadata transitions
  and validates their administrator/Skill-role preconditions at the remote
  serialization point, including after a non-fast-forward retry.
- Bypass repair first creates a durable
  `refs/gitim/quarantine/skill-<timestamp>-<head>` ref and journal pointing to
  the original local head. Under `commit_lock`, it then replays the quarantined
  commit range onto the accepted upstream while excluding Skill paths. Existing
  append-aware thread and metadata conflict resolution preserves normal GitIM
  changes from mixed commits. It verifies that every non-Skill local delta is
  represented and that the resulting Skill trees equal the accepted upstream
  trees before atomically moving the local branch. Skill-only commits disappear
  from the repaired branch but remain recoverable through the quarantine ref.
- Ordinary message/card/flow changes after a bypassed Skill commit therefore
  continue syncing. The hard-divergence discard path is disabled while a bypass
  journal is unresolved, so it cannot reset innocent descendants before repair.
  If a non-Skill delta cannot be replayed safely, the branch remains untouched,
  the quarantine ref remains durable, sync reports
  `skill_local_quarantine_blocked`, and no partial repair is pushed.
- Epoch-follow content replay excludes `skills/` and `archive/skills/` even for
  matching `.thread` files, and its resulting push still passes through
  `guarded_push`. A bypassed Skill history/discussion edit cannot re-enter the
  branch through the generic thread replay path.
- Every fetch-and-integrate path, including handler retry loops, pull-only sync,
  rebase recovery, and normal push sync, routes through one
  `guarded_integrate` coordinator. After fetch and before integration, every new
  commit touching
  Skill paths or root Skill receipts is transition-validated. A merge commit
  touching those paths is rejected; valid v1 mutations are always single-parent
  commits.
- Validation uses an accepted checkpoint stored under
  `.gitim/skill-validation.json`, containing the active epoch, last scanned tip,
  last accepted workspace administrator tree, last accepted commit/tree for
  each slug, and conflict state. The checkpoint is local derived data and never
  committed. Updates use a dedicated lock anchor plus atomic temp-file persist,
  so sync integration and transaction completion cannot lose each other's
  checkpoint advancement.
- A fresh clone does not trust the active epoch root by itself. It follows
  retained epoch predecessor/redirect metadata back to the initial no-Skill
  state, validates the workspace bootstrap, and replays only first-parent
  Skill-touching commits in order. At every epoch boundary it verifies that the
  new snapshot's workspace and per-Skill trees exactly equal the preceding
  accepted trees before advancing. Missing or corrupt predecessor history fails
  closed with `skill_epoch_validation_blocked`.
- A lagging follower first replays missed Skill transitions on the sealed
  predecessor branch through its seal tip, then compares that newly accepted
  state with the orphan snapshot. It never compares the snapshot directly with
  a stale pre-replay checkpoint.
- Epoch rotation is disabled while any Skill validation conflict exists, the
  outbound bypass journal is unresolved, or the working snapshot's Skill trees
  differ from the accepted checkpoint. A successful rotation copies only the
  fully accepted Skill state. This makes the epoch root safe for existing and
  fresh-clone validation without allowing a poisoned remote tree to become a new
  trust anchor.
- For every candidate commit, the daemon compares the immediately preceding
  accepted Skill tree with the candidate tree before exposing it.
- A valid mutation commit adds exactly one matching root receipt, carries the
  same `Gitim-Request-Id` trailer, and changes only the path set allowed for that
  receipt's operation.
- The pure transition validator checks actor permissions and expected revisions against the preceding accepted tree. Git author name must equal the receipt actor; this remains an audit check rather than cryptographic identity proof.
- Invalid metadata, missing revisions, hash mismatches, or illegal transitions mark the Skill `skill_sync_conflict`.
- The daemon refuses unpinned loads and every mutation for a conflicted Skill.
- A pinned revision remains readable during conflict only when both its immutable revision and matching publication record exist in the last accepted Skill state and its hash is valid. Candidate-only revisions remain proposal-inspection content.
- A non-fast-forward remote history rewrite never advances an existing
  checkpoint automatically. It records the divergent tip and fails closed
  without changing the last accepted read view.
- Repair is an explicit tracked-administrator Runtime CLI transaction. Its
  receipt identifies the invalid or divergent commit range and the prior
  accepted tree OID; the resulting commit restores the affected workspace or
  Skill control subtree exactly to that accepted tree. Incoming validation may
  scan past an invalid range only to a matching authorized repair commit, never
  exposes an intermediate tree, and then resumes normal transition validation.
  The retained epoch lineage lets a fresh clone reconstruct the same accepted
  tree and validate the repair. Generic metadata last-writer-wins is never used
  for Skill control files.

The normal sync loop needs no content merge for valid v1 Skill writes because
each accepted remote transaction is a complete fast-forward commit.
`guarded_push` and `guarded_integrate` are the only working-branch publication
and integration seams; tests enumerate call sites so a new handler cannot bypass
them. After an accepted Skill commit is integrated, a sync callback compares
workspace/per-Skill `event_revision` values with its cache and emits deduplicated
`skill_changed` invalidations. This gives every clone and frontend the same
refresh signal, not only the daemon that originated the mutation.

## Agent Loading Contract

The provider base prompt contains only this stable entry point:

```text
GitIM provides optional shared Skills and does not load them automatically.

When a message contains skill:<slug>@<revision>, run
gitim skill load <ref> before handling the related task.

When the user asks to discover, sediment, or maintain a Skill, run
gitim skill --help instead of guessing commands.

Loading a Skill does not grant permission to execute its scripts.
```

No Skill names, descriptions, bodies, management commands, argument lists, permission rules, or proposal states appear in the base prompt.

The Runtime does not pre-load referenced Skills. The provider decides when to call the CLI through its normal tool loop, just as it does for other GitIM operations.

`load` carries the remaining just-in-time contract: pinned archived revisions are marked `archived: true`; invalid, missing, corrupted, unpublished, or unpinned-archived refs fail without substituting another revision; and additional resource commands appear only when needed.

## Frontend Experience

### Slash Discovery

When the caret follows a token-start `/`, the composer opens a Skill popup:

- Search matches slug, display name, and description.
- Results are loaded from the active workspace and capped at 20.
- Arrow keys move selection, Enter inserts, and Escape closes.
- Selection inserts the current pinned `skill:<slug>@<revision-id>` reference.
- The popup does not execute or load the Skill.
- Mention and Skill popups are mutually exclusive.

The async lookup is owned by the current workspace, scope, query generation, and mounted component. Stale responses cannot update a newer composer.

### Message Rendering

A valid Skill ref renders as a compact Skill chip showing display name and abbreviated revision. Hover or focus shows slug, full revision, owners, and description. Clicking opens the Skill detail route.

Code spans and code blocks never become Skill refs.

If metadata is unavailable, the message still shows the raw stable ref and remains copyable.

### Skill Management

The frontend adds a Skills section with:

- Catalog list and search
- Current revision and revision history
- Owners and maintainers
- Open proposal count
- Proposal detail, bounded `SKILL.md` diff, and changed-resource manifest
- Proposal discussion
- Publish, reject, withdraw, and comment actions when authorized and connected through Runtime
- Copy-ref action for every published revision; candidate revisions expose proposal inspection actions only

Directory authoring and role/archive administration remain CLI-first. The frontend does not implement a general multi-file Skill package editor in this version. Browser-daemon mode exposes snapshot catalog metadata, published refs, history metadata, and proposal metadata as read-only. Package bodies, candidate resources, and mutation controls require a Runtime backend.

Every post-await state mutation uses the existing workspace/request ownership pattern. Skill SSE events carry:

```json
{
  "type": "skill_changed",
  "slug": "release-check",
  "kind": "proposal_commented",
  "event_revision": 12,
  "control_revision": 4,
  "proposal_id": "p-...",
  "proposal_state_revision": 3
}
```

`event_revision` orders every Skill change. `control_revision` is present for control-plane refresh decisions; proposal identifiers and state revisions let the store invalidate only affected proposal views. Frontend stores ignore events whose `event_revision` is not newer than the cached Skill event revision.

## API and Runtime Boundaries

`gitim-core` owns:

- Skill, revision, and proposal identifiers
- Metadata types and validation
- Package manifest hashing
- Permission checks
- Proposal state transitions
- Skill ref parsing and formatting
- Size and path constraints

`gitim-daemon` owns:

- Filesystem reads and writes
- Commit locking
- Atomic mutation and rollback
- Git attribution
- Private-index remote publication and fast-forward retry fencing
- Outbound and incoming Skill transition validation checkpoints
- Commit-keyed Skill catalog/read-view caching
- Skill-aware sync integration
- SSE events

`gitim-client` exposes typed methods for every daemon operation.

`gitim-cli` is the complete agent-facing management surface.

`gitim-runtime` exposes thin HTTP routes under `/im/skills` and does not duplicate business rules.

`gitim-wasm` exports pure protocol functions needed by `daemon-web`.

`daemon-web` owns browser-local snapshot metadata parsing, ref formatting, pagination, and read-only response construction. It does not claim that a publication transition was authorized, return `SKILL.md`/resource bytes, or mutate Skills. Agent execution always loads through a Runtime/Rust daemon that validated the accepted transition chain.

The frontend consumes Runtime/daemon-web APIs and owns only presentation, request ownership, capability gating, and local UI state.

## Success Criteria

1. An active agent can validate and create a standard package through the CLI.
2. Every active member can list and explicitly load the published revision without changing runtime-native configuration.
3. `gitim skill load` returns a bounded instruction body and resource index.
4. A frontend `/` selection inserts a pinned stable ref.
5. A receiving agent recognizes the ref and loads that exact revision through the CLI.
6. Old pinned refs continue to load after newer revisions are published or the Skill is archived.
7. Any active member can submit a proposal; only owners or maintainers can publish it.
8. Role and archival permissions match the table above.
9. Concurrent proposals preserve both immutable candidates.
10. A stale publish cannot overwrite a newer published revision.
11. Commit or push failure leaves no partially written published state and does not remove unrelated commits.
12. Skill lifecycle mutations appear in both Git history and `history.thread`.
13. Reads create no commits.
14. Invalid, oversized, escaping, symlinked, or hash-mismatched packages cannot be loaded or published.
15. Rust daemon authoritatively validates and loads packages; browser daemon advertises catalog-only capability and never claims package-load parity.
16. Existing Flow, message, provider, and runtime-native Skill behavior remains unchanged.
17. Every Skill HTTP/list surface enforces its documented pagination and response-size bounds.
18. A remote Skill write racing background sync or epoch rotation either wins a
    normal fast-forward publication or receives a non-fast-forward rejection;
    it cannot discard unrelated local or remote commits.
19. A daemon-bypassing local Skill commit is blocked before push, and an invalid
    fetched Skill transition cannot replace the last accepted read view.
20. Owner recovery is accepted by every clone only when the actor appears in the
    tracked workspace Skill administrator metadata.
21. A bypassed local Skill commit is preserved under a quarantine ref while
    later valid GitIM message changes are replayed and continue syncing.
22. Epoch rotation cannot promote conflicted or unaccepted Skill state into a
    snapshot trust boundary; a fresh clone reconstructs the same accepted state
    through retained epoch lineage.
23. A tracked administrator can repair an invalid or divergent Skill range
    without exposing the invalid intermediate state or force-pushing history.
24. Workspace administrator add/remove transitions are audited, cannot remove
    the final administrator, and block user departure while the role remains.
25. A Skill change integrated from another clone emits a deduplicated
    `skill_changed` invalidation after sync.

## Distribution Plan

The feature ships through GitIM's existing Rust CLI/daemon/runtime binaries and frontend deployment pipeline. No separate Skill service, package registry, or provider plugin is introduced.

Protocol additions are versioned additively. The CLI and Runtime expose stable error codes so older frontends can display a generic failure while newer clients provide Skill-specific recovery.

## Architecture and Code Quality Decisions

```text
local caller
    |
    v
typed Skill request + workspace-global request ID
    |
    +--> package snapshot + validation
    |
    v
immutable remote-tip read set
    |
    v
private Git index --> candidate tree --> pure transition validation
    |
    v
normal fast-forward push (remote ref is CAS)
    |
    +--> accepted read view --> bounded Skill reads
    |
    `--> normal sync --> inbound validation --> worktree integration --> SSE

local daemon-bypassing Skill commit
    |
    v
quarantine ref + journal --> replay only verified non-Skill deltas --> normal sync

invalid/divergent remote Skill range
    |
    v
last accepted read view + conflict health
    |
    `--> tracked-admin repair commit --> validator skips unexposed invalid range
```

The load-bearing boundaries are:

1. `gitim-core` owns canonical schemas, validation, transition authorization,
   ref parsing, hashing, media types, and stable error codes.
2. `gitim-sync` owns Git object plumbing, remote CAS publication, bypass repair,
   incoming history validation, checkpoint persistence, and epoch gating.
3. `gitim-daemon` owns actor resolution, package import, request journals,
   command dispatch, accepted read views, and Skill change events.
4. `gitim-client` and `gitim-cli` expose typed, progressively discoverable
   operations without duplicating domain rules.
5. `gitim-runtime` exposes bounded read/review APIs and local human-only
   administrator operations.
6. The frontend consumes capabilities and immutable refs; it never claims
   package-load or mutation support from daemon-web when those capabilities are
   false.

Complex state machines receive inline ASCII comments at their implementation
sites: the remote Skill transaction, incoming checkpoint advancement, bypass
quarantine/replay, proposal transition, and administrator repair validator.

## Failure Modes

| Code path | Production failure | Test | Handling | User-visible result |
|---|---|---|---|---|
| Package import | Source changes or contains a symlink during import | Mutation and filesystem race tests | Validate and copy once without following links | `skill_invalid_package` with path detail |
| Remote transaction | Concurrent writer moves the branch tip | Two-daemon CAS integration test | Re-read complete semantic set; retry only if unchanged | Success or structured stale response |
| Remote transaction | Crash after push before local cleanup | Phase-injected recovery test | Receipt lookup finalizes published result | Retry returns original result |
| Private Git work | Git subprocess hangs or concurrency saturates | Timeout and permit tests | Bounded permit plus subprocess deadline/kill | Retryable transport error and health counter |
| Local bypass | Mixed commit also contains messages | Quarantine/replay integration test | Durable quarantine ref; content-aware non-Skill replay | Sync continues or explicit blocked health state |
| Incoming validation | Commit bypasses daemon or touches illegal paths | Crafted-history tests | Keep last accepted view; mark conflict | `skill_sync_conflict`, pinned accepted refs still work |
| Remote rewrite | Fetched tip is not descendant of checkpoint | Force-push simulation | Fail closed; require tracked-admin repair | Conflict tip and repair command are shown |
| Epoch rotation | Snapshot contains unaccepted Skill state | Rotation gate/fresh-clone tests | Refuse rotation until checkpoint is healthy/equal | `skill_epoch_validation_blocked` in health |
| Proposal transition | Two maintainers publish from same base | Concurrent publish test | One fast-forward wins; loser becomes stale | Refresh fields identify new current state |
| Role lifecycle | Sole owner/admin is removed or departs | Transition and depart precondition tests | Reject before any mutation/depart phase | `skill_last_owner`, `skill_last_admin`, or role-present error |
| Archive move | Commit fails after files move locally | Local transaction rollback test | Restore path-local backup/index only | No partial archive; typed commit failure |
| Read view | Push succeeds but normal sync is delayed | Read-after-push integration test | Serve tree/blob data from accepted commit cache | Success with `local_state: pending_sync` |
| Cross-clone event | Originating daemon is not the viewing daemon | Two-clone sync/SSE test | Compare revisions after integration and emit invalidation | UI refreshes once; duplicates ignored |
| Frontend fetch | Workspace changes while request is in flight | Vitest stale-request test | Generation/ownership guard on every mutation | Old response cannot overwrite current workspace |

No path above is intentionally silent without both a test and an explicit health
or user-facing error.

## Performance and Capacity

- Package validation is capped at 256 files, 10 MiB total, 5 MiB per file, and
  64 KiB for `SKILL.md`; paths are streamed once into the immutable snapshot and
  canonical hash.
- Remote Skill Git work uses a per-workspace semaphore of four permits, a
  transaction deadline, and killable subprocess timeouts. The remote ref remains
  the correctness boundary; the semaphore limits local resource use only.
- Catalog caches are keyed by accepted commit ID. Proposal counts use the
  bounded `open_proposal_ids` index, so terminal proposal history does not enter
  catalog hot paths.
- `load` uses one recursive tree listing and one `SKILL.md` blob read. Additional
  resources remain on-demand, and text/diff responses have deterministic byte
  caps.
- Incoming validation walks only new first-parent commits that touch Skill
  paths. Checkpoints avoid replaying accepted history on normal startup.
- Fresh-clone validation can cross epoch lineage but filters for Skill-touching
  commits; retained epochs preserve correctness without parsing ordinary
  message-only history.
- Request receipts grow with mutations but are accessed by exact path. List and
  load operations never enumerate the receipt directory.

## NOT in Scope

- Runtime-native Skill installation or symlinking — would couple GitIM to
  provider-specific precedence and permission rules.
- Automatic catalog/body prompt injection — conflicts with the bounded,
  explicit-load model.
- Automatic script execution — loading instructions must not expand tool
  authority.
- Private per-agent Skills — this feature defines workspace-shared state.
- Cross-workspace marketplace or distribution service — requires a separate
  identity, trust, and publishing model.
- LLM or last-writer-wins content merge — Skill instructions require explicit
  human/agent review.
- Browser multi-file authoring in v1 — directory import remains a trusted local
  daemon operation.
- Offline remote-backed mutation queues — semantic convergence is deliberately
  postponed until a separate protocol is designed.
- Cryptographic authorization against hostile Git principals — tracked roles
  provide consistent protocol validation, not signature security.
- Per-read audit commits — reads remain side-effect free and Git history records
  mutations only.

No item above is added to `TODOS.md`; each is an intentional product boundary,
not forgotten maintenance work.

## Worktree and Dependency Strategy

The user selected one isolated worktree with sequential mergeable slices.
Shared protocol types and Git safety fences are upstream dependencies for every
consumer surface, so parallel worktrees would create avoidable protocol drift.

| Step | Modules touched | Depends on |
|---|---|---|
| Core domain and validator | `gitim-core/`, `gitim-wasm/` | — |
| Git transaction and sync fences | `gitim-sync/` | Core domain |
| Daemon read/write handlers | `gitim-daemon/`, `gitim-client/`, `gitim-cli/` | Core + Git safety |
| Provider load loop | `gitim-agent-provider/`, Runtime agent integration | Daemon load |
| Runtime read/review gateway | `gitim-runtime/` | Daemon/client |
| Frontend discovery and read views | frontend daemon-web, stores, composer, views | Core wasm + Runtime gateway |
| Collaborative administration | daemon/client/CLI/Runtime/frontend | All preceding control/read seams |

Execution is one lane:

```text
core -> Git safety -> daemon/CLI load -> provider E2E -> Runtime -> frontend
     -> collaboration/admin -> final cross-surface verification
```

Every node is a mergeable checkpoint. After each node, Cursor Grok and Kimi k3
review the scoped diff; accepted corrections land before the next node starts.
