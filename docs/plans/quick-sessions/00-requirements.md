# Quick Sessions Requirements

Status: Approved for implementation
Date: 2026-07-11

## Product intent

Quick Sessions provide a lightweight, top-level conversation surface for work that is too small for a task card and too isolated for a shared channel. A user can open the global hub, choose one agent, send an initial message, and continue the conversation without changing the agent's primary channel context.

The feature preserves GitIM's core model: visible collaboration data is plain text committed through the daemon, Git carries it across nodes, and provider execution remains local to the runtime that owns the selected agent.

## User experience

The desktop top bar contains a Quick Sessions entry. Hover previews the hub; click or keyboard focus keeps it open while the user interacts with it. The hub contains:

1. A list of active sessions across all agents in the workspace.
2. A compact create form with agent selection and the first message.
3. A conversation panel for the selected session.

Each row shows the title or a short pending-title placeholder, agent identity, latest-message preview, current status, compact ref, and updated time. The selected session supports sending a message, copying or dragging its ref, and archiving it. Archived sessions can be revealed with an explicit filter and remain readable by ref.

Quick Sessions use the existing design system: warm dark surfaces, restrained semantic color, comfortable spacing, rounded controls, functional motion, and monospaced technical identifiers.

## Creation and title contract

Creation requires only:

- A selected active agent.
- A non-empty first message.

The create request carries a client-generated Quick Session id. A retry with the same id and matching immutable fields returns the existing session instead of allocating another object.

The daemon creates the durable object and initial human-authored thread entry in one commit. The initial persisted status is `needs_title`.

The selected agent must set a concise title through `gitim session title <session-id> <title>` before its first reply. The daemon rejects an agent reply while the title is absent with `quick_session_title_required`. A successful title write changes the persisted status to `active` and records `title_source: api_set`.

The runtime treats a completed provider turn without both a title and an agent-authored reply as a failed session turn. It records a durable error state and stops automatic retries for the same input. A new human message clears that error and creates a new actionable turn.

## Durable object model

Active sessions are stored as:

```text
quick-sessions/<session-id>/session.meta.yaml
quick-sessions/<session-id>/discussion.thread
```

Archived sessions move to:

```text
archive/quick-sessions/<session-id>/session.meta.yaml
archive/quick-sessions/<session-id>/discussion.thread
```

`session.meta.yaml` contains:

- `id`
- `title` when set
- `title_source`: `none` or `api_set`
- `agent_id`
- `created_by`
- `status`: `needs_title`, `running`, `active`, `error`, or `archived`
- `created_at`
- `updated_at`
- `archived_at` when archived
- `archived_from` while archived
- `summary` when a context handoff has produced one
- `summary_updated_at` when a summary exists
- `last_message_preview`
- `error` when the latest actionable turn failed
- `processing_input_line`, `processing_started_at`, and `attempt_id` while a turn is claimed
- `last_completed_attempt_id`, `last_completed_input_line`, and `last_completed_line` after an agent reply
- the latest accepted human message request id for retry deduplication
- `revision`, incremented by every metadata mutation

`discussion.thread` uses the canonical GitIM message format and parser. The selected agent and creator are the only valid message authors. The creator can archive and unarchive the session. The session remains bound to its original agent.

Session ids use `qs-` followed by a 26-character Crockford Base32 ULID generated by the client. Validation happens before any path construction. If the id already names an object with different immutable fields, creation returns `quick_session_id_collision`.

## Runtime isolation

Provider execution state is local to the workspace runtime:

```text
<workspace>/.gitim-runtime/quick-sessions/<session-id>.state.json
```

The state contains the provider resume token, usage snapshot, token estimate, context-reset state, last attempted input line, and last completed input line. It is written atomically with mode `0600` on Unix.

Every quick session has an independent provider context. It inherits the selected agent's provider, model, effort, system prompt, environment, profile, and repository working directory. It never reads or writes the agent's primary provider token.

The selected agent's existing loop is the single execution scheduler for both primary and quick-session turns. It processes them sequentially, preserving provider-profile safety without a second polling loop or cross-loop lock. Each cycle prioritizes primary IM input and then processes at most one actionable Quick Session, preventing quick-session traffic from starving normal collaboration.

An actionable session has `needs_title` or `active` status, is assigned to the current agent, and has a creator-authored line newer than `last_completed_input_line`. Before provider execution, the runtime claims the highest current creator input line through the daemon. The claimed line is the inclusive upper bound of the input batch. The claim persists `running` status, the input line, a start timestamp, and an attempt id in one commit. This durable claim prevents another recovery path from executing the same input concurrently while allowing later human messages to queue behind the running turn.

A startup scan discovers actionable sessions even when the relevant Git commit predates the daemon poll cursor. It also converts stale `running` claims into a visible `error` state instead of repeating an execution whose external side effects are unknown. Claims and completions are compare-and-set operations on `attempt_id`; a late provider or CLI completion cannot write into a newer turn.

## Provider turn contract

The quick-session prompt identifies the session, its durable ref, the latest transcript window, and the exact CLI operations available:

- `gitim session title <session-id> <title> --attempt-id <attempt-id>`
- `gitim session send <session-id> <body> --reply-to <input-line> --attempt-id <attempt-id>`
- `gitim session send <session-id> --stdin --reply-to <input-line> --attempt-id <attempt-id>`
- `gitim session summarize <session-id> --stdin --attempt-id <attempt-id>`

The agent must communicate with the session only through these commands. Primary channel/DM/card messages are outside the quick-session turn unless the user explicitly requests escalation.

Provider streaming events are tagged with `scope: quick_session`, `session_id`, `attempt_id`, claim `revision`, and local `context_generation`. Existing activity consumers treat a missing scope as `agent_main`. Main-session UI ignores Quick Session events. The Quick Session store accepts streaming events only while their attempt id matches the durable active claim and their context generation is current; metadata-only events use revision ordering.

## Context pressure and handoff

Usage and context pressure are tracked per Quick Session. When a session crosses the runtime warning threshold, the next prompt requires the agent to write a concise durable summary with `gitim session summarize` and emit `[[RESET]]`. The runtime clears only that Quick Session's provider token after verifying the summary was updated, then increments the local `context_generation`. The next turn starts a fresh provider context using the durable summary and a bounded recent transcript window. Results and events captured under an older generation are discarded.

Provider self-managed-context declarations remain authoritative. For such providers, the runtime preserves the per-session token and does not initiate a runtime-side reset.

Workspace token totals continue to aggregate under the selected agent and provider, while live context occupancy remains scoped to the Quick Session.

## Cross-node behavior

Quick Session metadata and transcripts commit and sync through Git. Any writable human node, including the browser daemon, can create, read, continue, archive, and unarchive a session. Provider state and streaming remain on the node that owns the selected agent.

When the owning node receives the Git changes, the agent loop whose handler matches `agent_id` discovers the actionable session and executes it locally. The initiating node receives the title and reply through normal Git synchronization. If the owning node is offline, the session remains waiting and executes after that node returns.

Native runtime mode builds the picker from local and configured fleet agent snapshots. Browser mode has no runtime-liveness source, so it uses active workspace handlers and labels them as unverified until a matching agent runtime responds. The daemon validates that the selected handler exists and is not departed; execution eligibility remains the owning runtime's responsibility.

The browser daemon implements the same durable schema, validation, permissions, title gate, archive paths, and commit shape as the Rust daemon. State-transition rules live in `gitim-core` and are exposed through `gitim-wasm` so both writers use the same revision and status logic. The browser daemon does not execute providers.

## Reference contract

The stable ref is:

```text
session:<session-id>
```

An optional line target is:

```text
session:<session-id>:L000001
```

Core and frontend parsing recognize refs only at valid text boundaries. A Quick Session row and ref token are draggable into channel and card composers; dropping inserts text into the scoped draft and never sends automatically. Reference previews resolve title, agent, status, summary or latest preview, and a bounded transcript window.

## API contract

Daemon IPC operations:

- `create_quick_session`
- `list_quick_sessions`
- `read_quick_session`
- `send_quick_session_message`
- `set_quick_session_title`
- `set_quick_session_summary`
- `claim_quick_session_turn`
- `mark_quick_session_error`
- `archive_quick_session`
- `unarchive_quick_session`

Runtime HTTP endpoints under `/workspaces/{slug}`:

- `POST /im/quick-sessions`
- `GET /im/quick-sessions?archived=false`
- `GET /im/quick-sessions/{id}`
- `POST /im/quick-sessions/{id}/messages`
- `POST /im/quick-sessions/{id}/archive`
- `POST /im/quick-sessions/{id}/unarchive`

Title, summary, and error transitions are daemon operations used by the selected agent or runtime. The browser worker exposes the user-facing create/list/read/send/archive/unarchive methods through the existing backend abstraction.

## Safety and consistency invariants

1. The daemon is the only writer in native/runtime mode.
2. Session ids are validated before joining paths.
3. Metadata and thread mutations hold the daemon commit lock and roll back filesystem changes when commit fails.
4. Archived sessions are immutable except for unarchive. Archiving a running session clears its claim so late title, summary, and reply writes are rejected; unarchive restores the title-derived waiting state.
5. Agent replies cannot precede the title gate.
6. A Quick Session never mutates the primary agent session token or primary context-pressure state.
7. Main and Quick Session provider executions for one agent never overlap, and every Quick Session execution has a durable input-line claim.
8. Scoped activity events cannot update another session or the main activity panel.
9. Browser writes honor the epoch redirect fence and repository lock, and use the core transition rules through wasm.
10. A drag/drop action inserts a ref into the intended workspace and composer scope only.
11. Client retries and late provider completions are idempotent by request or attempt id.
12. Quick Session events and responses carry revisions so clients ignore stale delivery.

## Acceptance criteria

1. A user can create and open a Quick Session with an agent and first message.
2. The selected agent can set the title and reply using the session CLI.
3. An agent reply before title creation returns `quick_session_title_required` and does not modify the thread.
4. Primary and Quick Session provider contexts remain independent across multiple turns and restarts.
5. Primary activity UI ignores Quick Session events; each Quick Session applies only its matching events.
6. The owning runtime executes a session created by another Git-synced node, including a browser node.
7. Startup discovery processes actionable sessions that predate the current poll cursor.
8. A failed or incomplete provider turn does not spin; new human input can retry it.
9. Context handoff updates the durable summary and resets only the target Quick Session token.
10. Archive removes the session from the default list while preserving read and ref resolution.
11. Dragging into a channel or card inserts the stable ref into the correct draft without sending it.
12. Ref previews resolve active and archived sessions, including optional line targets.
13. Rust daemon, runtime, CLI, browser daemon, HTTP client, and frontend tests cover their contract boundaries.

## V1 boundaries

- One selected agent per session.
- No reassignment or multi-agent routing inside a session.
- No task workflow fields, boards, checklists, or status transitions beyond conversation lifecycle.
- No provider-state migration between nodes.
- No hard delete from the product UI.
